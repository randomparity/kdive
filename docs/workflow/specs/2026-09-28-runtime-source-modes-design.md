# Container runtime input permissions (#2864)

## Scope and authority

The approved campaign scope is issue #2864, token `q2864-a748bf21`; exclusions are empty.
The operator approved the complete issue and its verification on 2026-09-27.
Normalize copied runtime source and the manifest generator before fingerprinting, preserving
bytes and required read/execute behavior. Keep the existing provenance validators strict.

## Design

The final Dockerfile stage owns the boundary: immediately after its source/script COPYs,
run `chmod -R a+rX,go-w` on `/app/src` and the copied manifest script. This grants readable
files and traversable directories, preserves existing executable bits, and removes group/world
write. The image already creates root-owned copies. The builder and caller checkout stay untouched.
No interface, data model, caller migration, dependency, or validator change is needed.
ADR-0705 records this build boundary choice. Failure of chmod aborts the Docker layer.

## Success

A controlled source context with directories 0775 and ordinary files 0664 reproduces the
existing fingerprint rejection before the fix; the fixed image builds and installs its manifest.
The runtime source and generator remain byte-identical to the build inputs, except the existing
build-info stamp and generated bytecode. They are readable to the runtime user, directories are
traversable, and group/world write is absent. Existing image smoke checks pass, including Compose.
Existing manifest tests continue rejecting writable paths.

## Failure model

- Actors and deployments: trusted image builders in local Docker and CI; final non-root runtime.
- Invariants and assets: unchanged shipped source bytes; immutable root-owned fingerprint inputs;
  strict attestation; runtime readability and directory traversal.
- Accepted failure classes: network/base-image/dependency outages still fail the build; no fallback.
- Covered elsewhere: symlink/ownership and altered fingerprints remain rejected by bootstrap
  attestation and its existing manifest tests. Build context content remains the builder's trust.

## Threat model

- Boundary inventory: checkout mode metadata crosses into root-owned image COPYs and then into
  fingerprinting; only copied source and manifest-script inputs are normalized.
- Untrusted parties: runtime users cannot write these inputs; source content is trusted build input.
- Threats and mitigations: inherited writable modes allow replacement; remove group/world write
  before manifest creation. Preserve bytes; do not broaden ownership or weaken fingerprint checks.
- Out of scope: making malicious source content trustworthy, already outside the build trust model.
